# Security Policy

## Supported versions

Security fixes are applied to the latest release on `main`. The project is in beta; pin a commit if you need reproducibility. **0.4.2** is the first release that contains the hardening described below; earlier 0.4.x releases should not be used with untrusted repositories or prompts.

## Published audit

An independent audit of 0.4.1 (November 2026) is published at [docs/security/2026-11-audit.md](docs/security/2026-11-audit.md). It documents the trust-boundary and credential-handling issues fixed in 0.4.2; raw credential values, local paths and ready-to-run PoC payloads are not included.

## Reporting a vulnerability

Do not open a public issue for a vulnerability. Use GitHub private vulnerability reporting (Security → Advisories → Report a vulnerability) on the repository. Include the affected version/commit, a minimal reproduction, and the impact. We aim to acknowledge reports within 7 days and to agree a disclosure timeline before any public write-up.

## Security model and boundaries

- **Local-first.** Harness-Mesh runs as a local Python process. It does not operate a hosted service and does not upload your prompts, model inventories, or state database anywhere. Model calls are made by the installed harness CLIs on your machine.
- **Credentials stay with the harnesses.** Configuration parsing may read local harness settings and model catalogues to discover authorised models. Model discovery takes `base_url` and `api_key` only from the environment and user-level files (`HARNESS_MESH_CONFIG`, `$XDG_CONFIG_HOME/harness-mesh/`, `~/.config/harness-mesh/`, `~/.harness-mesh/`); files inside the checkout never decide the credential destination. `DiscoveredModel.provider` is a short enum-shaped label: a provider registry stored as a mapping, an over-long value or a credential-shaped string falls back to the harness name, so API keys and JWTs cannot enter the model object, the ledger or a tool response. `discover_harness_models` projects models through a field whitelist, and `list_skills_and_plugins` redacts MCP server `env` values. Transcripts, diffs and checkpoints are redacted (environment values and high-confidence key shapes) before they are persisted or placed in a prompt. The Artificial Analysis key comes from `ARTIFICIAL_ANALYSIS_API_KEY` and is sent only in the `x-api-key` header to `artificialanalysis.ai`.
- **Network access.** The market layer sends HTTPS GET requests only to `openrouter.ai/api/v1/models`, `models.dev/api.json`, `epoch.ai/data/benchmark_data.zip` and `artificialanalysis.ai/api/v2/language/models/free`. Each response is capped at 25 MB and 20 seconds, one provider refresh is capped at `market.total_timeout_seconds` (default 60 s), the `User-Agent` is `harness-mesh/<version>`, and a redirect must stay on the same host. The Epoch archive is read with `zipfile`, only for the benchmark CSVs named in the configuration; entries with an absolute path or a `..` segment are rejected, and the expanded archive is capped at 80 MB. Requests carry no prompts, file paths, model inventories, task identifiers or workspace data. Model discovery also performs HTTPS GETs to a harness's model endpoint; it requires HTTPS (plain HTTP is accepted only for loopback), rejects userinfo, and does not follow redirects. Both clients set `trust_env=False`, so proxy and custom-CA environment variables do not silently reroute or intercept those requests. `market.enabled: false` or `HARNESS_MESH_OFFLINE=1` stops every outbound market request, and `HARNESS_MESH_OFFLINE=1` additionally stops discovery HTTP while leaving local CLI enumeration available. Dispatch reads the local cache; a completely cold cache waits at most eight seconds (`market.wait_seconds`) for a refresh and then continues with the local tiers. Snapshots and the merged catalogue remain in the local `market_snapshots` table. The Artificial Analysis free tier is limited to 100 requests a day and to internal use; do not redistribute its data. Epoch AI data is CC BY 4.0: only aggregated percentiles are cached locally, and the attribution `Benchmark data: Epoch AI, 'Capabilities & benchmarking', https://epoch.ai/benchmarks (CC BY 4.0)` appears in `hmesh market show` and in every routing decision.
- **Prompt and output trust boundary.** Repository files, `AGENTS.md` / `CLAUDE.md`, skill files, harness stdout, and upstream task diffs are *data*, not instructions for the mesh process. They are bounded and quoted in prompts; they must not be treated as authorisation to change routing, permissions, or credentials. Instruction files must be regular files inside the workspace: symlinks and sensitive paths are rejected before their content reaches `get_project_context` or a dispatch prompt, and boundary-like tags are escaped after NFKC normalisation.
- **Worktree isolation.** Isolated tickets run in `.harness-mesh/worktrees/<task_id>`. `read_only` tickets run in a disposable worktree and cannot be applied. Changes only reach your primary checkout through an explicit `apply_task_patch`. Worktree isolation covers files in that checkout; it does not isolate the shared Git directory or your user permissions. Mesh disables hooks, fsmonitor, pager, external diff and protocol.ext for its own Git commands. A worktree `.git` pointer must be a regular file whose `gitdir` resolves under the primary repository's `.git/worktrees/` and whose backlink returns to that worktree; the guard hashes the pointer and gitdir path in addition to `.git/config`, `.git/info/attributes` and `.git/hooks`, and aborts the ticket with `git_metadata_tampered` if any of them changes after an assignment. Worktree reuse requires a matching `.harness-mesh-worktree.json` marker. Sensitive files are excluded from diffs, the ledger and `apply_task_patch` by resolved path, so nested `.env`/`*.pem`/`id_rsa` files and case-varied names are filtered too. Merge applies require a clean target and roll back on failure; apply verifies newly created symlinks and rejects paths that escape the workspace.
- **Local state.** The SQLite ledger, transcripts, diffs, generated MCP configs, and worktrees live under `.harness-mesh/`. The directory is created/tightened to `0700`; `state.db`, `-wal` and `-shm` are `0600`. The directory may contain sensitive source excerpts — keep it out of commits, backups and shared archives. `.gitignore` excludes it by default, but a cloned repository can still ship a tracked copy; a `.harness-mesh/state.db` that was tracked in Git is not treated as trusted configuration. On open, 0.4.2 rewrites legacy credential-shaped `discovered_models.provider` rows and checkpoints/vacuums the ledger so old bytes leave the database and WAL.
- **Workspace boundary.** The MCP server and CLI refuse to start from `$HOME`, `/`, or a directory outside Git unless `auto_init_repo` is enabled. The CLI and the MCP server both resolve a cwd under `.harness-mesh/worktrees/` back to the primary project root, and both refuse a task worktree as the workspace root, so an explicit `--workspace` that names a worktree is rejected; run from the project root or set `HARNESS_MESH_WORKSPACE`. Request-level `workspace_root` values are resolved through symlinks and checked against `allowed_workspace_roots`, which defaults to the service workspace. Context previews skip sensitive paths. `hmesh install` and `hmesh doctor` apply the same check. **Configuration trust:** only `--config`, `HARNESS_MESH_CONFIG`, `$XDG_CONFIG_HOME/harness-mesh/config.yaml`, `~/.config/harness-mesh/config.yaml` and `~/.harness-mesh/config.yaml` are trusted; the packaged example is a read-only fallback. Workspace configuration files are untrusted repository content and are ignored by default. `HARNESS_MESH_TRUST_WORKSPACE_CONFIG=1` merges only non-executable fields (market, routing, sizes, quotas) from a workspace file and never harness commands, binaries, credentials, `state_dir`, workspace allowlists, skill/plugin roots or approval settings. `hmesh install` does not read workspace configuration and never registers a workspace path as `HARNESS_MESH_CONFIG`.
- **Shared memory.** Project context keys are capped at 128 characters, entry content at 4,000 characters and rendered memory at 6,000 characters. Authors must match a configured harness or `controller`; this only validates the claimed name, not provenance. Entries are labelled `controller`, `worker`, or `auto`; only `controller` entries render as verified memory. The MCP server derives the label from lineage, and the CLI does the same, so a worker shell cannot write into the verified block; `router.update_project_context` defaults to `auto`. Auto-recorded and worker entries render in `<project_unverified_memory>`, and delimiter-like text is escaped case-insensitively.
- **Third-party agents.** Each harness has its own permission system, data policy, and terms of service. The five built-in harness configurations default to `auto_approve: true`; this injects approval bypass flags (for example Claude `--dangerously-skip-permissions`, Codex `--full-auto`, ZCode `--mode yolo`) for isolated worktrees. `workspace_mode: shared_write` suppresses those flags unless `auto_approve_shared_write: true`. Because `zcode -p` defaults to yolo, ZCode is started with `--mode build` instead (measured headless on ZCode 0.17.0: `build` denies file writes and shell, `edit` allows writes but denies shell, `guarded` still allows both); set `restricted_mode: edit` in the ZCode harness `extra` block to allow file edits. Approval bypass is a convenience, not a sandbox. Review your provider's terms and enable approval policies appropriate to your environment.
- **MCP tool pre-approvals.** `hmesh install --approve` writes harness-side allow rules for individual MCP tools. The default level, `dispatch`, covers the eleven read tools and the three dispatch tools. `--approve all` additionally covers `report_quota_status` and `update_project_context`; `apply_task_patch` and `install_integration` are always manual and are never written into a harness allow rule. Rules go to Claude Code `~/.claude/settings.json` (`mcp__harness-mesh__<tool>`), Codex `~/.codex/config.toml` (a managed `[mcp_servers.harness-mesh.tools.<tool>]` block with `approval_mode = "approve"`), and Antigravity `~/.gemini/config/config.json` (`mcp(harness-mesh/<tool>)`). ZCode and DeepSeek Harness need no setting. The installer keeps a `<file>.harness-mesh.bak` copy, writes through a temporary file, re-parses the result, and restores the previous content if validation fails; `--approve none` and `--uninstall` remove only entries this tool wrote. A pre-approval skips the harness prompt for that tool; it does not widen the harness sandbox, filesystem access, or network policy. Independently of harness approvals, the MCP server refuses every write tool when `HARNESS_MESH_READ_ONLY=1` and refuses a caller resolved to a running assignment the controller-only write tools (`apply_task_patch`, `install_integration`, `cancel_task`, `report_quota_status`). `hmesh apply` and `hmesh install` apply the same gate in the CLI.
- **Harness integration discovery.** Integration detection in `list_harnesses`, `get_integration_status`, `hmesh doctor`, `hmesh status` and `hmesh integrations` reads configured binary paths, app bundle paths and existing MCP/plugin registrations only. It starts no subprocess and creates no file, including the macOS ZCode shim: a plan reports the shim path, but only a real install creates it. `plan_integration` is read-only and returns a `plan_id` derived from the plan and the current target files. `install_integration` rewrites another application's global configuration, so it is a write-class tool and stays manual. It refuses a caller resolved to a running Assignment as a worker, refuses `HARNESS_MESH_READ_ONLY=1`, and refuses any `plan_id` that does not match a freshly computed plan. `hmesh doctor` executes a registered command only when it is the current interpreter with `-m harness_mesh.mcp_server`; any other shape is reported without being run. `integration.ignore` only suppresses hints; it uninstalls nothing, and it is written to a user-level config file, never into the checkout.
- **Recursion ancestry.** `max_call_depth`, trace-chain cycle rejection and `max_active_assignments` are enforced across separate MCP server processes. Each running Assignment records the depth, the trace chain and the pid of the harness process the adapter spawned. A nested MCP server rebuilds its lineage from the running Assignment whose pid appears in its process ancestor chain (`os.getppid()` followed by `ps -o ppid=`), then from a cwd under `.harness-mesh/worktrees/<task_id>`, then from the legacy ticket request; the result is combined with any inherited `HARNESS_MESH_*` values by maximum/union. `hmesh dispatch` uses the same lineage resolution (the shared `harness_mesh.lineage` module, the same ledger) and treats `--call-depth` as a lower bound only, so a worker cannot drop its inherited depth by running the CLI from a shell. Codex CLI 0.166.0-alpha.5.1, measured on 2026-11-01, did not forward the host environment to MCP child processes (the child saw only the variables declared in the MCP configuration), so on Codex the pid ancestry and the worktree cwd are the effective protections. The agent-writable `.harness-mesh-lineage.json` is accepted only when the ledger already records that ticket as running with a worktree containing the current directory, and a worktree path derived from cwd always wins over a conflicting marker. The active-assignment count comes from the shared `state.db`; rows whose pid no longer exists are closed as `ended_error` with `error_reason=stale` instead of holding a slot, including the per-ticket conflict check. A cancelled or crashed dispatch closes its own open row as `ended_error` (`cancelled` / `dispatch_exception`) rather than leaving it running. Known limitation: the active-assignment check counts live rows and inserts the new row in two separate statements, not one transaction, so dispatches that start at the same instant can each see a free slot and together exceed `max_active_assignments`; the cap limits steady-state concurrency, not a simultaneous burst.
- **Built-in runtime environment.** The DeepSeek built-in runtime strips variables whose names contain `API_KEY`, `TOKEN`, `SECRET`, or `PASSWORD` before running its shell tool, while keeping `PATH`, `HOME`, `LANG`, and similar process state. This reduces accidental credential exposure; it is not a filesystem or network sandbox. CLI harnesses inherit the mesh process environment by design because their own login and provider configuration depend on it; use dedicated accounts or keys for automation.
- **Supply chain.** Python dependencies are declared with lower/upper bounds in `pyproject.toml`. `mcp` is pinned below 2.x because this project uses the MCP 1.x FastMCP API. No third-party source is vendored. Run `pip-audit` or your normal dependency scanner before production rollout.

## Fixed in 0.4.2

An independent audit of 0.4.1 reported 42 findings (4 critical, 14 high). 0.4.2 closes all critical items, thirteen of the fourteen high items and the low-cost medium items (H-14 is partially mitigated and listed under Known limitations):

- **Workspace config as code execution:** workspace `config/harnesses.yaml`, `.harness-mesh/config.yaml` and `config/harnesses.example.yaml` no longer control `binary`, `binary_paths`, `version_args`, `model_list_args`, `execute_template`, `state_dir`, workspace allowlists, skill/plugin roots or approval settings; user-level config and explicit `--config` keep working. `hmesh doctor` only runs the current interpreter's mesh entrypoint.
- **Credential leakage:** provider values are sanitised before entering a model object; `discover_harness_models` returns a field whitelist; `list_skills_and_plugins` redacts `env`; transcripts, diffs and checkpoints are redacted before storage and prompts; the transcript resource is capped; legacy `provider` credentials are purged from the ledger and WAL.
- **Credential exfiltration:** model-discovery auth sources are restricted to environment and user-level files; HTTPS-only (loopback exception), no userinfo, no redirect following, `trust_env=False`, and `HARNESS_MESH_OFFLINE=1` also stops discovery HTTP.
- **Worktree Git execution:** `.git` pointer validation and guard hashing; worktree reuse requires a marker; `task_id` is validated and cross-process conflicts are rejected without touching the other ticket; `_safe_remove_dir` refuses the worktree root.
- **Diff/apply integrity:** sensitive paths are filtered by resolved path (nested and case-varied included) for diffs, ledger and apply; merge requires a clean target and rolls back on failure; new symlinks are verified and Git quoted paths decoded.
- **Write gates:** `HARNESS_MESH_READ_ONLY=1` refuses all write tools; workers are refused controller-only writes; `--approve all` excludes `apply_task_patch` and `install_integration`; CLI `hmesh apply`/`install` use the same checks; `hmesh context set` derives provenance from lineage.
- **State hygiene:** state directory `0700`, ledger files `0600`, generated MCP configs `0600`; DSH backups and uninstall are atomic and `0600`.

## Known limitations

- A worker that fully detaches from the mesh process tree (`setsid`, cleared `HARNESS_MESH_*`, cwd outside any worktree) can still be resolved as a controller by the ancestry-based lineage check. Worktree isolation and the server-side write gates limit what such a caller can do, but they are not a cryptographic identity boundary.
- Approval bypass flags remain a convenience, not a sandbox. A prompt-injected harness can still act within its own filesystem and network permissions.
- CLI harness workers inherit the mesh process environment, including provider credentials, because the vendor CLIs need them to authenticate.
- Merge/apply rollback restores tracked files and the index; an untracked file that existed before a failed apply and was rewritten by the patch has no backup.
- Repository content that is not valid UTF-8 can still make a Git read fail; the ticket fails rather than being silently truncated.
- User-level `base_url` values are checked for scheme, userinfo and loopback rules but are not restricted to a host allowlist, because self-hosted gateways are a supported deployment.

## Hardening checklist

1. Keep `.harness-mesh/` out of version control, backups you do not control, and shared machines.
2. Use dedicated API keys or subscription accounts for automation.
3. Prefer `workspace_mode: isolated_worktree` and review diffs before `apply_task_patch`.
4. Do not enable `auto_approve` or `auto_approve_shared_write` for untrusted repositories or untrusted prompts.
5. Run the MCP server with the narrowest filesystem scope you can; `HARNESS_MESH_WORKSPACE` sets the primary project root.
6. Rotate credentials if a transcript or local state directory is exposed, then open the ledger once with 0.4.2 and verify `PRAGMA user_version` is `1` and raw scans no longer find the old values.
7. Keep `--approve` at `read` or `dispatch`. `apply_task_patch` and `install_integration` are always manual by design; review what the harness can reach in either case.
8. Leave `HARNESS_MESH_TRUST_WORKSPACE_CONFIG` unset for repositories you did not write; set it only when you accept that the workspace file can tune non-executable routing and market fields.
9. After upgrading, restart every harness that runs `hmesh-mcp`; the server process must be started from the 0.4.2 code for the new gates to apply.
