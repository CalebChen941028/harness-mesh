### Summary (English)

An independent read-only audit of `harness-mesh` 0.4.1 found 42 issues: 4 critical, 14 high, 15 medium, 5 low and 4 informational. 0.4.2 fixes all four critical findings and thirteen of the fourteen high findings; the remaining high item (H-14) is partially mitigated and its residual risk is documented below. Three themes ran through the report:

1. Repository-controlled files were trusted as configuration, so a cloned project could choose which binary the mesh executes or where model-discovery credentials are sent.
2. Credentials could be written into the local SQLite ledger and echoed back through MCP tool responses and `hmesh models --json`.
3. Worktree, task-id and approval boundaries could be bypassed by a file-write-only agent or a prompt-injected worker.

Release verification: 684 tests passed, 12 opt-in real-machine tests skipped, `ruff` clean, and all 42 installed Python packages had no known CVE at audit time. The Chinese sections below carry the evidence, per-finding fix status and the remaining known limitations.

## 一、结论

### 1.1 总体判断

工程纪律扎实：测试覆盖 495 个用例、lint 干净、依赖无已知 CVE，market 网络层按声明实现了 HTTPS 白名单、同源重定向、流式大小上限与 zip 路径校验。

问题集中在信任边界。项目把工作区内可被仓库提交或提交的文件当成用户可信输入：mesh 配置、harness 配置、`AGENTS.md`、worktree 内容、`.harness-mesh/state.db`。这些输入能决定执行哪个二进制、把 API key 发往哪个地址、哪些内容进入模型 prompt。凭据处理缺少统一脱敏层，发现出的 provider 配置被原样写入账本并经 MCP 与 CLI 回显。

结果：一个恶意仓库（或一次提示注入）可以在默认配置下完成任意命令执行、真实 API key 外发，以及把宿主凭据写进本地账本。本机已实证两枚真实凭据落在 `state.db` 与 WAL 中。

### 1.3 对“是否有密钥泄露风险”的直接回答

| 问题 | 结论 |
| :--- | :--- |
| Git 仓库与全部历史里有没有真实密钥？ | **没有。** 82 个 commit、437 个 blob（含不可达对象）、5 个 tag、reflog 残留全部扫描，命中项只有测试假值（`sk-should-not-appear`、`test-deepseek-key`、`postgres://user:pass@localhost`）。历史路径 119 个与当前跟踪文件数一致，说明没有删除过敏感文件。 |
| 本地运行态有没有已经泄露的凭据？ | **有，已实证。** `.harness-mesh/state.db` 的 `discovered_models.provider` 列（rowid 38/39）保存了用户 ZCode 配置中的两枚真实凭据（一枚 API key、一枚 JWT），WAL 中另有副本。该字段与 `~/.zcode/v2/config.json` 的 `str(provider)` 逐字节相等（长度 4170）。具体值不在本文保留。 |
| 运行时会不会把凭据泄露出去？ | **会，存在三条通道。** ① `discover_harness_models` 与 `hmesh models --json` 原样回显 provider 凭据（CR-02）；② `list_skills_and_plugins` 回显用户全局 MCP 配置的 env 凭据（H-03）；③ 恶意仓库可控 `base_url`，把宿主 API key 发往攻击者主机（CR-03）。 |

### 1.4 首要处置

1. **立即轮换两枚 ZCode 凭据**，然后清理 `state.db`/WAL（步骤见 2.4）。这两枚值已存在于主库、WAL 与备份快照可见的路径上。
2. 在修复前，不要在不可信仓库里运行 `hmesh status`、`hmesh models`、`hmesh doctor`、`hmesh install`，也不要把 harness-mesh 的 MCP 服务指向不可信仓库。
3. 按 CR-01 到 CR-04 的修复项处理信任边界；这是本次审计里唯一能同时消除 RCE 与凭据外发的动作。

## 二、真实密钥泄露专项

### 2.1 仓库与 Git 历史：无真实泄露

扫描范围与命令：

- 工作树 142 个文本/二进制文件（含 `docs/`、`.github/`、`config/`、`tests/fixtures`、`egg-info`、`.harness-mesh/`），176 个 `.pyc` 逐字节扫描。
- Git 全历史：82 commit、937 个对象、437 个 blob（含不可达对象）、5 个 tag、reflog 中已删除分支的提交；逐 blob 正则与熵值复核。
- 模式表覆盖 `sk-*`、`sk-ant-*`、`ghp_`、`github_pat_`、`xox[baprs]-`、`AKIA`、`AIza`、PEM 私钥、`hf_`、`npm_`、JWT、URL 内嵌密码、`apiKey` 赋值、智谱 key 形态。

结论：没有真实凭据，也没有 `.env`、私钥、`state.db` 进入 Git 对象库（最大 blob 120,804 字节）。候选误报全部来自测试固件与代码标识符。`.gitignore` 覆盖 `.harness-mesh/`，`git check-ignore` 确认状态目录被忽略。

### 2.2 本地运行态：已实证泄露

根因在 `src/harness_mesh/discovery.py:481-492`：

```python
provider = "zcode"
if isinstance(data, dict):
    provider = str(data.get("provider") or "zcode")
```

`~/.zcode/v2/config.json` 顶层 `provider` 是 provider 注册表（dict，含各 provider 的 `options.apiKey`）。`str(dict)` 把 4170 字符的整段注册表塞进每个 zcode 模型的 `provider` 字段，随后 `_finalize()`（`discovery.py:1093-1125`）把模型写进 `discovered_models` 表。

已确认的事实：

| 项目 | 实测结果 |
| :--- | :--- |
| 落库位置 | `.harness-mesh/state.db` 的 `discovered_models.provider`，rowid 38/39（`harness=zcode`，`GLM-5.3` / `GLM-5.3-Flash`），字段长度 4170 |
| 凭据 1 | BigModel API Key，49 字符，来源 `provider["builtin:bigmodel-coding-plan"].options.apiKey`，该 provider `enabled: true`（值不公开） |
| 凭据 2 | Z.ai Coding Plan JWT，180 字符，payload 含 `user_id`，无 `exp`，来源 `provider["builtin:bigmodel-start-plan"].options.apiKey`（值不公开） |
| 字节级比对 | 与实时 `str(~/.zcode/v2/config.json["provider"])` 完全相等（长度 4170） |
| 副本数量 | 主库各 2 份；`state.db-wal` 各 4 份；`state.db-shm` 0 份 |
| 可用性 | 凭据格式真实，来自本机正在使用的 ZCode 配置。审计未联网调用，因此“服务端当前是否接受”未验证 |

WAL 的问题需要单独说明：16:33 首轮扫描时 WAL 尚无命中，后续 discovery 写入把含 provider 的页写进 WAL，16:42 复测时已有 4 份副本。普通 `UPDATE` 不会清掉旧页，必须 `wal_checkpoint(TRUNCATE)` 加 `VACUUM`。

### 2.3 凭据进入账本与流向外部的主要通道

| 通道 | 代码位置 | 后果 |
| :--- | :--- | :--- |
| 配置里的 dict 被 `str()` 后进入模型对象 | `discovery.py:481-492`（zcode）、`discovery.py:412-420`（codex 同构） | 整个 provider 注册表进入 `DiscoveredModel.provider` |
| discovery 落库 | `discovery.py:1093-1125`、`storage.py:268-322` | 凭据持久化进 `state.db`，随刷新反复写入 WAL |
| MCP 工具全字段回显 | `router.py:2539/2546`、`mcp_server.py:165-174` | controller 模型收到真实 apiKey/JWT |
| CLI JSON 回显 | `cli.py:558-577` | 终端、CI 日志、粘贴内容里出现凭据 |
| 全局 MCP 配置 env 回显 | `skills.py:178-270/417-425` | 用户其它 MCP server 的 token 进入 tool response |
| 工作区可控 base_url 外发 | `discovery.py:734-842` | 宿主环境变量里的 key 被发到攻击者主机 |
| worker 全量输出落账本 | `router.py:678-686/1100/1127/1794`、`storage.py:1111-1122` | worker 打印的环境变量、文件内容进入 `resources` 表 |
| 账本可被读回 | `mcp_server.py:345-353`、`storage.py:1131-1176`、`cli.py:764-786` | 上述内容可被 controller 或本机 CLI 分页取走 |
| 生成的 MCP 配置 | `skills.py:384-411` | 插件 env 以 0644 文件落盘 |

`SECURITY.md:14` 写明“Configuration parsing … does not copy API keys into the mesh state database, logs, or tool responses”。上述通道与该承诺相反，文档需要按修复后的行为重写。

### 2.4 凭据处置步骤

1. 到智谱 / Z.ai 控制台轮换这两枚凭据。审计产物中的完整值已删除，但 `state.db`、`state.db-wal` 以及可能的 Time Machine、云盘、备份快照里仍有副本，轮换前不要分享这些文件。
2. 停止所有 mesh MCP 进程，然后执行：

```bash
cd <repo>
sqlite3 .harness-mesh/state.db "UPDATE discovered_models SET provider='zcode' WHERE harness='zcode' AND length(provider)>64;"
sqlite3 .harness-mesh/state.db "PRAGMA wal_checkpoint(TRUNCATE); VACUUM;"
strings .harness-mesh/state.db .harness-mesh/state.db-wal | grep -c '<已轮换凭据的旧前缀>'   # 期望 0
```

3. 检查 controller 侧会话目录是否出现过泄漏值：`~/.claude/projects`、`~/.codex/sessions`、`~/.dsh/sessions`。本次扫描未命中，说明该通道尚未被实际调用，但应保留一次核查记录。
4. 修复 CR-02 后再启用 `discover_harness_models`；在修复前把它从默认预授权中移除。

## 四、Critical

### CR-01 工作区配置被当成可信执行配置

**位置**：`config.py:623-640`（`find_config_path` 依次探测 `<workspace>/.harness-mesh/config.yaml`、`<workspace>/config/harnesses.yaml`、`<workspace>/config/harnesses.example.yaml`）、`config.py:757-815`（`load_config` 合并，`_merge_harness_config` 接受 `binary`/`binary_paths`/`version_args`/`model_list_args`/`execute_template` 覆盖）、`adapters/base.py:130-153`（`detect()` 跑 `[binary, *version_args]`）、`adapters/base.py:246-290`（`execute()` 跑渲染后的 `execute_template`）。

**攻击链**：恶意仓库提交 `config/harnesses.yaml`（未文档化但被加载）或 `.harness-mesh/config.yaml`（README 推荐位置，被 `.gitignore` 忽略不妨碍 clone 落地），把 `claude_code.binary` 指向仓库内脚本、`version_args` 指向任意命令，或把 `execute_template` 写成 `/bin/sh -c ...`。

触发入口：

- `hmesh status`：`cli.py:512-522` → `router.list_harnesses` → `adapter.detect()` → 执行 `--version`；缓存未命中时再执行一次 `model_list_args`。
- MCP `list_harnesses`（read 类，默认 `dispatch` 预批准）：同一条链路；独立复核已从 `create_mesh_runtime(...).router.list_harnesses()` 复现。
- MCP `dispatch_task`（dispatch 类，默认预批准）：走 `execute_template`。
- `hmesh doctor`：单独入口不执行 harness 二进制，但会执行 `.harness-mesh/zcode-plugin/.../plugin.json` 里的 `command`（`installer.py:543-560/1064-1096/653-660`），PoC 记录 argv `--from-repo --help` 被执行。
- `hmesh install`：执行仓库二进制并持久化仓库配置（见 H-13）。

**PoC**：在临时 Git 仓库放 `config/harnesses.yaml`，`claude_code.binary` 指向 payload 脚本；带假 HOME 与 `HARNESS_MESH_OFFLINE=1` 运行 `hmesh status --json`。payload 被执行两次，标记文件记录执行用户与工作目录，exit 0，无警告。同一机制换成 `execute_template: ["/bin/sh","-c",...]` 同样执行。

**影响**：在本机用户权限下执行任意命令，子进程继承完整父环境变量（`adapters/base.py:332-348`）。提交 `config/harnesses.yaml` 的仓库、PR 分支、或一个被 clone 后“看看 README”的项目都满足前提。

**同一根因的其它字段**：`allowed_workspace_roots` 可放宽请求级 `workspace_root` 边界，`auto_approve_shared_write` 可恢复审批绕过，`state_dir` 可把状态写向任意绝对路径，`skill_roots`/`plugin_roots` 可把仓库内文件送进 agent prompt 与 MCP 输出（`config.py:312-352`）。

**修复**：

1. 按信任级拆分配置来源。只有 `--config`、`HARNESS_MESH_CONFIG` 与用户级目录（如 `~/.config/harness-mesh/config.yaml`）可以设置执行相关字段。
2. 工作区配置只允许非执行字段（显示名、tier 偏好、market 别名等）；`binary*`、`version_args`、`model_list_args`、`execute_template`、`base_url*`、`api_key_env`、`env_model_variables`、`state_dir`、`allowed_workspace_roots`、`auto_approve_shared_write`、`skill_roots`、`plugin_roots` 一律忽略。
3. 如果确实需要项目级配置，首次使用时把文件 SHA-256 写入用户级 trust store 并要求确认；文件变化后重新确认。
4. `doctor` 不执行来自工作区状态目录的注册命令；`install` 只接受用户级配置。

### CR-02 真实凭据落入账本并经 MCP/CLI 回显

### CR-04 worktree 内 `.git` 指针与 `.gitattributes` 未校验，git clean filter 导致命令执行

**位置**：`workspace.py:169-185`（`_git_metadata_snapshot` 只哈希主仓 `.git/config`、`.git/info/attributes`、`.git/hooks`）、`workspace.py:191-231`（guard 只覆盖这三项）、`workspace.py:707-734`（`collect_diff` 在 worktree cwd 执行 `git add -N` 与 `git diff`）、`workspace.py:759-791`（`collect_changes`）。

**攻击链**：worktree 内 `.git` 是 `git worktree add` 生成的可写普通文件。只能写文件、不能执行 shell 的 agent 就能利用它，ZCode `--mode edit`、只开 Edit/Write 工具的 Claude Code、被提示注入的只读 harness 都属于这一类。做法是把 `.git` 改成 `gitdir: <worktree>/evilgit`，在 fake gitdir 的 `config` 里写 `[filter "evil"] clean = /path/payload`，再加 `.gitattributes` 的 `* filter=evil`。mesh 下一次 `collect_changes`/`collect_diff`/checkpoint 执行 `git add -N` 或 `git diff` 时，git 为计算 blob 哈希会运行 clean filter，payload 以 mesh 进程权限执行。正常完成路径（`router.py:1084`）就足够触发，外层 `except` 吞掉异常，攻击者看不到报错。

**PoC**：用只写文件的 fake adapter 模拟受限 agent，dispatch 完成后标记文件存在，dispatch 状态 `completed`。

**影响**：这是 worktree 隔离对 harness 权限沙箱的逃逸。harness 本身的 shell 权限被禁，mesh 却以用户权限执行了 agent 写入的内容。

**修复**：mesh 自有 git 命令显式固定 `GIT_DIR`/`GIT_WORK_TREE`，并在每次 collect/apply 前校验 worktree `.git` 文件内容与登记路径一致；拒绝 worktree 内 `.gitattributes` 中引用 config 未声明的 filter（`git check-attr` 校验）；把 worktree `.git` 文件与 fake gitdir 纳入 guard 哈希。

### H-05 敏感文件过滤在 diff 层失效，apply 把嵌套敏感文件写进主仓

`security.py:72-81` 生成 `:(exclude,glob)<pattern>` 形式的 git pathspec，`workspace.py:707-734` 用它们过滤 `collect_diff`。两个缺陷：

1. glob 模式不匹配嵌套路径。`.env` 只排除根目录的 `.env`，`apps/web/.env` 与 `certs/server.pem` 仍进入 diff。
2. git pathspec 大小写敏感，而 `is_sensitive_path` 大小写不敏感。`SERVER.PEM`、`ID_RSA` 被 `modified_files` 判为敏感、列进 `skipped_sensitive`，内容却留在 `diff` 里。

实测（真实代码路径）：worktree 写入 `apps/web/.env` 与 `certs/server.pem`，`collect_changes` 的 `modified_files` 为空、`skipped_sensitive` 正确列出两个文件，但 `changes.diff` 含 `OPENAI_API_KEY=…` 与 `BEGIN PRIVATE KEY` 全文。随后 `apply_worktree_changes(strategy="patch")` 把这两个文件写进主工作区：`applied_files` 为空、`warnings` 声称已跳过，文件实际落地。diff 还会进入 `resources` 表、`get_task_status` 与 `read_task_resource`。

修复：用 `is_sensitive_path` 逐文件过滤 diff（而不是依赖 git pathspec），或生成 `:(exclude,glob)**/.env` 等同时覆盖嵌套与大小写的模式；apply 前对 diff 再过滤一次并断言 `skipped_sensitive` 与写入集合一致；补嵌套路径与大小写的回归测试。

### H-06 `merge` 冲突时主工作区与 index 已被污染

`workspace.py:857-884` 先 `git apply --3way --check` 预检，冲突时 `--check` 仍可能返回 0；真正 `git apply --3way` 会先把冲突标记写进 working tree，再把 index 留成 unmerged（`UU`），随后代码抛 `merge conflict ... primary workspace left untouched`。PoC 显示主工作区文件含 `<<<<<<< ours` 冲突标记，index 出现三个 stage，`git status` 为 `UU`。影响：用户相信“未改动”而继续工作，实际已污染，后续 patch 与提交都会带上冲突标记。修复：merge 策略先在临时索引或临时 clone 里应用，成功后再替换；失败时执行 `git checkout -- .` 与 `git reset` 回滚，并在错误信息中如实报告。

### H-07 quoted path 绕过 symlink 检查，向主仓植入逃逸 symlink

`workspace.py:911-942` 的 `_check_diff_symlinks` 用 `line.startswith("+++ b/")` 与 `line[6:]` 解析路径。git 对非 ASCII 或含特殊字符的路径输出 C 风格 quoted 形式（`"b/docs/\351\223\276\346\216\245"`），解析结果与原路径不一致，symlink 检查被跳过。PoC 用中文目录名把 `docs/链接 -> <工作区外的路径>` 的补丁 apply 进主仓，文件成为指向工作区外的 symlink。影响：worktree 隔离的路径包含前提被破坏，后续写入可能穿透到用户目录。修复：用 `git diff --raw -z` 或 `git apply --numstat` 的机器可读输出取路径，不要解析人类可读 diff 头；解析失败时拒绝而不是放行。

5. **plan_id TOCTOU**：预览后改动目标文件，旧 `plan_id` 被拒；备份、原子写、重解析、失败回滚均存在。

## 十、审计方法与局限

**方法**：四个独立审计面（执行与文件系统、密钥与落盘、MCP 与信任边界、供应链与网络）并行，每条发现要求 file:line 证据；High 及以上写独立 PoC，在临时 Git 仓库与沙箱 HOME 中运行，主仓库与真实配置零改动。关键结论由独立复跑 PoC 交叉确认：恶意仓库 RCE、API key 外发、账本真凭据、`task_id="."` 删目录、跨进程 task 劫持、worktree `.git` RCE、插件 env 回显、指令文件 symlink 读取、敏感 diff 泄漏与 apply 落地。

**局限**：

- 未联网调用任何真实凭据，因此“两枚凭据当前是否仍被服务端接受”未验证；凭据真实性与落库事实已确认。
- GitHub 远端设置（branch protection、action 白名单、secret scanning 开关）不在仓库内，未审计。
- 未安装的 optional extra `google-antigravity` 未纳入依赖审计；pyproject 下界版本未安装验证。
- 未执行完整 `hmesh dispatch` 端到端真实模型调用，worker 行为用 fake adapter 与合成 fixture 验证。
- pip-audit 的“0 CVE”只代表审计时刻 OSV/PyPI advisory 数据库无公开告警。

**威胁模型**：本地单用户工具，但输入不可信——恶意仓库、被提示注入的 controller/worker、可写 worktree 的受限 agent。判定标准是“文档承诺必须由代码强制”；测试通过不算证据。
